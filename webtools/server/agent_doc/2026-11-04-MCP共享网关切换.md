## 三、为什么不设 transport 配置项

`url` 与 `transport` 是**同一件事的两种写法**。两个字段就能互相矛盾，而矛盾的配置比没有配置更难查。所以 transport 由 URL 形态推导：

```
http://…/sse           → sse
http://…/agentgeex/mcp   → streamable-http
```

回滚时只要把 `BFF_MCP_URL` 设成 `/sse` 结尾，transport 自动跟着回去 —— 不存在"改了一半"的状态。

## 四、★ 顺手修掉的真 bug：自检在看别人的表

`code_freshness()` 原本靠 `/tmp/win3_mcp_sse.pid` 找"BFF 连的那个 MCP 进程"。切到网关后，这个 pid 文件指向**我们已不再连接的 31888 进程** —— 拿它比内核 mtime，等于**拿旁观者的表报自己的时间**。

改为：**谁在监听 `settings.mcp_url` 的端口，就查谁**（`lsof -t -iTCP:{port} -sTCP:LISTEN`），transport 无关、事实自证。pid 文件只作 legacy 兜底（`pid_source: "pidfile"` 会明说）。

同时修了第二个坑 —— **`ps -o lstart=` 受 locale 影响**：

```
中文环境: 三 11/ 4 08:04:29 2026     ← strptime("%a %b ...") 解析失败
C 环境:   Wed Nov  4 08:04:29 2026   ← 正常
```

解析失败会静默走到 fallback（读 pid 文件 mtime）。实测后果：网关 08:04 启动、内核 07:43 修改，被误判成「旧码」。**反向更危险**：旧码 + 更新的 pid 文件 mtime 会被判成「最新码」，于是没人去重启。

修法：subprocess 传 `LC_ALL=C / LANG=C`，并约定「按端口找到的 pid 不许回退到 pid 文件时间」——那是两个不同进程的时间，不能混。

另加一道：**同端口多个监听进程 → 直接判 stale 并点名**。双监听意味着老进程没退干净，"改了代码但仍旧码"极难察觉。

   → 该进程已停止，无残留 `--transport=sse` 进程。

### ★ 教训：`lsof` 按端口看两端，会造出"看起来成对"的假连接

| 做法 | 可信度 |
|---|---|
| `lsof -iTCP:PORT`，把两端地址配成一条连接 | ❌ 临时端口复用会骗人 |
| `lsof -iTCP:PORT -sTCP:ESTABLISHED` 计数 | ✅ 只对数，不配对 |
| `lsof -p <PID> -iTCP`（进程维度） | ✅ 看这个进程真正连了谁 |

代价：我差点因为一条假证据去"保护"一个并不存在的外部依赖。
**判断"谁在连谁"，不能靠端口号相同就认作同一条连接。**
