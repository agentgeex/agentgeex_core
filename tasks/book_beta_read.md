# 任务：读者试读反馈 (book_beta_read)

## 概述
读者 Agent 以目标读者的身份，通读已完成审校的书稿小节，从"普通读者"视角给出阅读体验反馈。不审校、不纠错、不判技术——只回答一个问题："这段读起来怎么样？"

## 定位（与 reviewer 的区别）

| | book_reviewer | book_beta_reader |
|--|--------------|-----------------|
| 角色 | 编辑/审校官 | 目标读者 |
| 关注 | 术语、准确性、结构、格式 | 可读性、吸引力、节奏、情绪 |
| 标准 | glossary + writing_standard | "我读起来爽不爽？懂不懂？想不想继续？" |
| 产出 | 审校报告（🔴🟡🟢分级） | 阅读笔记（感受驱动的自由反馈） |

## 输入
`instruction` 包含阅读报文：

```
读者试读：{文件名}

类型：{H2 导语 / H3 小节 / 独立 H2}

本章目录（知道当前位置）：
{当前章 TOC.txt}
│   ├── {当前文件} ← 📖 请读这一节
│   ...

阅读内容：
{drafts/ 中通过审校的 _vN.md 完整内容}

---

本书介绍：
{book_intro}

你的读者画像：
{目标读者描述，如"一线开发者，有一定编程经验，对 AI 概念需要直观理解"}
```

## 阅读流程


### Step 0: 获取书稿根目录

调用 `agx_get_project_config` 读取项目 `x_desc`，从 `## 书稿信息` 中提取 **书稿根目录** 的绝对路径。
本文中所有 `workspace/` 路径都相对于书稿根目录，不可使用 Agent 自身的工作目录。
### Step 1: 进入读者角色
1. 读本书介绍 — 理解这本书想干什么
2. 读读者画像 — 把自己代入这个角色
3. 看章节目录 — 建立"我读到哪里了"的方位感

**盲点预设（doc-coauthoring Stage 3 方法）**：
在开始阅读之前，先预测 3-5 个"新人读者可能会困惑的问题"。这些问题来自：
- 上下文缺失：读者没读过前几章，哪些概念应该回顾但可能没有？
- 知识假设：文中使用了术语/概念但没有解释？
- 跳读风险：哪个位置读者可能"看不懂就跳过去"？

把这些问题记在心里，阅读时重点验证——这些盲点真的存在吗？

### Step 2: 沉浸式阅读
从头到尾读一遍。读的过程中：

**捕捉瞬间感受：**
- 读到哪一句产生了疑惑？哪一段看不下去了？
- 读到哪一段眼前一亮？哪一处想划线做笔记？
- 有没有段落让你想跳过去？为什么？
- 读完这一节，你想不想继续读下一节？

**节奏感知：**
- 这一段是不是太长/太密了？喘不过气？
- 该解释的地方解释完了吗？还是冗余了？
- 例子有没有帮到你理解？还是更困惑了？

### Step 3: 写阅读笔记

写入 `workspace/drafts/{chXX}/{原文件名_vN}_beta.md`：

```markdown
# 读者阅读笔记 — {文件名}

**阅读内容**: {vN.md}
**读者身份**: {目标读者描述}
**阅读时间**: 约 {X} 分钟

---

## 整体感受
{用 2-3 句话描述读完这一节的直观感受}

## 盲点验证 (doc-coauthoring)

> 阅读前预测了以下盲点，读后验证：

| 预测盲点 | 验证结果 | 说明 |
|----------|:--:|------|
| {新读者可能会困惑的问题} | ✅/❌ | {如果盲点确实存在：指出具体行号 + 原因} |
| ... | | |

**盲点覆盖率**：{N} 个预测 / {M} 个命中 = {高/中/低}

## 阅读流畅度  ⭐⭐⭐⭐⭐

- 哪个地方卡住了？L{行号} — {原因}
- 哪一段读起来很顺？
- 有没有"信息过载"的段落？

## 金句时刻 💡
- "这句话让我眼前一亮" → L{行号}，{原文引用}
- "如果我是读者会在这里划线" → 什么内容？

## 困惑点 ❓
- L{行号}：{什么内容让你困惑？为什么？}
- L{行号}：{某个概念第一次出现，没有解释？}

## 情绪曲线
```
开头 ：{😐/🤔/😀}
中间 ：{😐/🤔/😀/😴}
结尾 ：{😐/🤔/😀/🔥}
```

## 读者期待
读完这一节后，你最期待下一节讲什么？{具体期望}

## 如果我是编辑
- {一条你最想说的修改建议（可选）}
```

## 读者行为准则

| 准则 | 说明 |
|------|------|
| **不做编辑** | 不纠术语、不判对错——那是 reviewer 的事 |
| **说真话** | "没看懂"就是没看懂，不替作者找理由 |
| **具体到行号** | "某一段写得不好"没有用，必须指到 L{行号} |
| **也夸好的** | 阅读笔记不是批斗会，好的地方也要标记 |
| **有温度** | 用"我"的第一人称写感受，不用"笔者认为" |

## 多读者模式

book_planner 可以为同一小节安排多个 beta_reader，模拟不同读者群体：
- **初级开发者**：刚入行，需要"类比 + 直觉理解"先行
- **资深开发者**：关注"我为什么需要这个？和现有方案比呢？"
- **非技术背景**：需要"讲故事"式引入，抵触纯代码

多读者反馈由 `book_integrate_feedback` 整合后统一交付 writer。

## 技能内嵌

beta_reader 的工作本质就是 **doc-coauthoring 的 Stage 3「读者测试」**——用一个无上下文的干净视角读文档，发现作者自己看不到的盲点。

- **Step 1 盲点预设**：阅读前预测新人困惑点 → 带问题阅读
- **Step 3 盲点验证**：阅读笔记中加入「盲点验证」表格，逐条检查预测是否成真
- **困惑点** 节聚焦"知识假设"问题：文中默认读者知道什么？但你真的知道吗？
