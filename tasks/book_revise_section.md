# 任务：小节修订 (book_revise_section)

## 概述
写作师根据审校报告（`_review.md`）或读者反馈整合（`_beta_integration.md`），针对性修改已有的书稿小节。对照反馈的 🔴🟡 项逐条处理，产出 `_v{N+1}.md`。

## 输入
`instruction` 包含修订报文：

```
修订任务：{文件名}

类型：{H2 导语 / H3 小节 / 独立 H2}

审校报告摘要：
{_review.md 中 🔴 和 🟡 项，或 _beta_integration.md 中的精选反馈}

当前版本路径：
workspace/drafts/{chXX}/{文件名}_vN.md

当前版本内容：
{_vN.md 完整内容}

---

修订要求：
1. 逐一处理上述反馈中的 🔴 和 🟡 项
2. 输出 _v{N+1}.md
3. 对某个审校建议有异议的，在文件末尾注明 `[审校异议] {原因}`
4. 不扩大修改范围——只改反馈涉及的内容
```

## 修改流程


### Step 0: 获取书稿根目录

调用 `agx_get_project_config` 读取项目 `x_desc`，从 `## 书稿信息` 中提取 **书稿根目录** 的绝对路径。
本文中所有 `workspace/` 路径都相对于书稿根目录，不可使用 Agent 自身的工作目录。
### Step 1: 解析修订任务
1. 读当前版本内容 — 这是要修改的基底
2. 读审校报告摘要 — 逐条理解每个 🔴🟡 项
3. 判断每条反馈的修改策略

### Step 2: 逐条处理反馈

| 反馈类型 | 处理策略 |
|---------|---------|
| 术语不一致 | 统一到 glossary 标准写法 |
| 内容错误 | 修正技术描述、补全代码 |
| 风格问题 | 调整语气、压缩/展开段落 |
| 衔接断档 | 加过渡句、调整结构 |
| 读者困惑 | 加解释、加类比、重组复杂段落 |
| 视角差异 | 可接受 → 不改；有道理 → 有节制地改 |

### Step 3: 写出新版本

写入 `workspace/drafts/{chXX}/{文件名}_v{N+1}.md`：

```markdown
{修改后的完整内容}

---
<!-- 修订记录 -->
- _v1 → _v2: 修复术语"transformer"→"Transformer"(L42)，补全 import 语句(L78)，压缩开头(350→200字)
```

**版本号规则：**
- 当前是 `_vN`，新版本 = `_v{N+1}`
- 修订记录放在文件末尾的 HTML 注释中，不影响正文

### Step 4: 处理异议

如果对某条审校建议有异议（如 reviewer 建议改 A，但你坚持 B），不直接拒绝——在文件末尾注明：

```markdown
[审校异议] L42 "transformer" 大小写：在"Transformer 模型"固定大写，但"transformer 架构"作为通用术语可小写。当前用法根据上下文区分，请 reviewer 复核。
```

### Step 5: 自审
- [ ] 是否处理了所有 🔴 项？
- [ ] 是否处理了所有 🟡 项？
- [ ] 修改后是否引入了新问题？
- [ ] 版本号是否正确递增？

### Step 6: 结案
```
agx_finish_task(
  task_run_uuid={当前 run_uuid},
  status="succeeded",
  result={输出文件路径},
  summary="{文件名}：_v{N}→_v{N+1}，处理 🔴{X}项 🟡{Y}项，异议{Z}项"
)
```

## 异常处理

| 场景 | 处理 |
|------|------|
| 找不到当前版本 `_vN.md` | `agx_finish_task(status="failed")`，summary 写"找不到 {路径}" |
| 反馈中有不清楚的描述 | 不猜测，标记 `[反馈不明确，保持原样]` |
| 某反馈建议与另一条冲突 | 同时标注两条，选更合理的，在修订记录说明原因 |
| 修改后超出字数范围 | 注明显著偏差原因（如"增加 300 字以解释 XXX"） |

## 执行约束
- 只改反馈涉及的内容，不顺手"优化"其他段落
- 不改变文件名中的小节编号
- 修改后必须保留修订记录（末尾 HTML 注释）
- 异议必须给出具体理由，不能只说"我觉得没问题"
