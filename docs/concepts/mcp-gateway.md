# AgentGeeX Unified MCP Gateway

> Status: **live and verified** (2026-11-04)
> Applies to: AgentGeeX `c20b2bf` and later
> Tested on: macOS 14.5 (arm64, Python 3.13) / Ubuntu (x86_64, Python 3.14)

## Overview

AgentGeeX ships three MCP services: `agentgeex` (100 tools), `mysql-srv` (5 tools), `redis-srv` (7 tools).

Historically these three services were launched over **stdio** by each client separately — OpenClaw gateway launched one set, DSH launched another, and every session launched yet another. The result: **the same three Python processes replicated at a scale of clients × sessions**.

This design consolidates the three services into a **single-process HTTP gateway**, isolated by URL path, with every client sharing one copy:

```
agentgeex  →  http://127.0.0.1:31890/agentgeex/mcp    streamable-http   100 tools
mysql-srv  →  http://127.0.0.1:31890/mysql/mcp      streamable-http     5 tools
redis-srv  →  http://127.0.0.1:31890/redis/mcp      streamable-http     7 tools
```

**Hard constraint: not a single tool name may change.** The `agx_*` tool names hardcoded in task specifications, prompts and notices, together with the prefixes each platform adds automatically, must stay exactly as they were in the stdio era — otherwise migrating would amount to rewriting every prompt in the system.

---

## 1. Why change

### 1.1 The fundamental problem with stdio

stdio is a "one process per client" model, with the process lifetime bound to the client. That was fine in the single-machine, single-client era, but AgentGeeX is multi-platform and multi-session concurrent:

| Symptom | Measurement |
|---|---|
| Each active session runs its own three-service set | 6 sessions on 10.0.0.13 → **18 processes / 1.80 GB** |
| Processes grow linearly with sessions | every new session adds a set; nothing is reclaimed automatically |
| The three processes duplicate framework overhead | three FastMCP apps instantiated separately, 260.6 MB |
| Handshake cost repeated per session | stdio 741 / 529 / 805 ms |

### 1.2 Why merging processes is safe

First, dispel a misconception: **the merge is not about sharing a database connection pool.**

The three pools are in fact independent:

```
mcp_server.pool      max_connections=20   id=4406001104
mcp_server_redis.pool  max_connections=5    id=4420142096
→ are the two the same object? False
mcp_server_mysql.py    has no pool at all; all 5 sites call pymysql.connect() fresh each time
```

So the real gain from merging is **framework and interpreter overhead**: three FastMCP instances → one. Not connection reuse.

## 2. Design selection

### 2.1 A rejected option: FastMCP's native `mount(prefix=)`

FastMCP offers `mcp.mount(sub, prefix="mysql")`. It looks like the least effort, but **it rewrites tool names**:

```
agx_get_global_config  →  prefix renaming of the mysql_query_database kind
```

Consequence: the tool names hardcoded in task specifications, the `mcp__server__tool` prefixes generated by each platform, and the names referenced in notices and the skill library would **all break**. That is not a migration; it is a rewrite of every prompt in the system.

**Rejected.**

### 2.2 The adopted option: Starlette path Mount

```python
MOUNTS = (
    ("agx", "mcp_server"),
    ("mysql",   "mcp_server_mysql"),
    ("redis",   "mcp_server_redis"),
)
app.mount(f"/{path}", sub_app)     # path isolation, tool names untouched
```

How the two compare:

| | native mount(prefix=) | Starlette path Mount |
|---|---|---|
| Tool names | rewritten | **completely unchanged** |
| Changes to service files | required | **zero** |
| Code volume | small | one ~200-line entry file |

**The only cost is one entry file, in exchange for zero change to tool names.** A very good trade.

### 2.3 Why stateless

The gateway runs with `stateless_http=True`: every call is an independent POST and the server keeps no session state.

Two important properties follow:

1. **`GET /xxx/mcp` returning 405 is normal**, not a fault. Stateless mode does not stream; only POST is served.
2. **After a service-process restart, clients recover without restarting** — there is no long-lived connection to break.

## 3. The thread pool: a new risk introduced by merging

Merging three services into one process means they share one anyio thread pool. **The default ceiling of 40 becomes the new single point of failure.**

Measured (concurrent load on all three services):

| Scenario | Response of the *other* service |
|---|---|
| Baseline (no concurrency) | 21 ms |
| 30 threads occupied | 47 ms |
| 50 threads occupied | **4972 ms** ← all 40 tokens exhausted, queued |

That is: one service saturated by 50 slow queries makes **an entirely unrelated service wait 5 seconds**. This is the new coupling the merge introduces.

The fix: raise the shared ceiling at startup.

```python
anyio.to_thread.current_default_thread_limiter().total_tokens = 120
```

After the change: with 50 concurrent `SLEEP(5)` calls, the redis service responds in **51 ms**; with 100 threads occupied it is still 41 ms.

The default is `DEFAULT_MAX_THREADS = 120`, overridable with `--max-threads`.

## 4. Deployment

### 4.1 Prerequisites

- Python ≥ 3.9 (uses `tuple[...]` / `list[str] | None` annotations, all guarded by `from __future__ import annotations`)
- Dependencies: `fastmcp`, `starlette`, `uvicorn`, `anyio`
- Server-side credentials go in `agx_config.json` (**not** in the client configuration)

### 4.2 How to start

```bash
python agx_mcp/mcp_gateway.py \
    --port 31890 \
    --host 127.0.0.1 \
    --max-threads 120 \
    --mount agx,mysql,redis     # optional, mount only some services
```

Full parameter table:

| Parameter | Default | Environment variable | Description |
|---|---|---|---|
| `--host` | `127.0.0.1` | `MCP_GATEWAY_HOST` | bind address, **do not change to 0.0.0.0** (no authentication) |
| `--port` | `31890` | `MCP_GATEWAY_PORT` | listening port |
| `--max-threads` | `120` | — | shared anyio thread ceiling, see §3 |
| `--mount` | all | — | comma-separated subset, e.g. `agx,redis` |
| `--log-level` | `info` | — | uvicorn log level |
| `--no-selfcheck` | off | — | skip the startup self-check |

> ⚠️ The corresponding option in `mcp.sh` is called `--threads` (the script converts it to `--max-threads`). When invoking python directly the flag is `--max-threads`; do not mix the two.

After startup it self-checks the three endpoints; the log looks like:

```
[gateway] listening on http://127.0.0.1:31890
[gateway]   /agentgeex/mcp  <- mcp_server
[gateway]   /mysql/mcp  <- mcp_server_mysql
[gateway]   /redis/mcp  <- mcp_server_redis
[gateway] thread limiter total_tokens = 120
[gateway] selfcheck OK   http://127.0.0.1:31890/agentgeex/mcp
```

### 4.3 Linux (systemd --user)

```ini
# ~/.config/systemd/user/agx-mcp-gateway.service
[Unit]
Description=AgentGeeX MCP Gateway (agx + mysql + redis, path-mounted)
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
WorkingDirectory=/home/<user>/project/agx
ExecStart=/home/<user>/project/agx/.venv/bin/python agx_mcp/mcp_gateway.py --port 31890
KillSignal=SIGTERM
TimeoutStopSec=20
Restart=always
RestartSec=5
StandardOutput=journal
StandardError=journal
SyslogIdentifier=agx-mcp-gateway

[Install]
WantedBy=default.target
```

```bash
systemctl --user daemon-reload
systemctl --user enable --now agx-mcp-gateway
loginctl enable-linger $USER     # critical: otherwise the service stops after logout
```

`Type=simple` with a foreground process is a deliberate choice: the main process *is* the service process, so when the process dies the service dies, which is what makes `Restart=always` actually work. (Counter-example: `Type=oneshot` plus a launcher script — the script exiting is recorded as success, so after the main process is killed the service still shows as active.)

### 4.4 macOS (PM2)

```bash
pm2 start agx_mcp/mcp_gateway.py --name agx-mcp-gateway \
    --interpreter ./venv/bin/python -- --port 31890
pm2 save
```

On macOS `pm2 startup` (boot persistence) is not enabled; after a reboot run `pm2 resurrect` manually.

### 4.5 The ops script `mcp.sh`

A second lifeline alongside PM2 (no PM2 / PM2 broken / foreground debugging / systemd-launchd supervision):

```bash
./mcp.sh {start|stop|restart|status|check|logs|run} \
         [--port N] [--host IP] [--threads N] [--mount a,b] [--force]
```

**Mutually exclusive with PM2**: while PM2 reports online, `start` / `stop` are refused (exit code 1) and a pm2 hint is printed.

The reason: `pgrep -f agx_mcp/mcp_gateway.py` also matches the copy supervised by PM2. Without that guard it kills the wrong process and triggers an autorestart that fights for the port (this actually happened once). To genuinely detach from PM2: `pm2 delete agx-mcp-gateway && ./mcp.sh start`.

## 5. Client integration

### 5.1 General principles

1. **Use `streamable-http` for `transport`** (some platforms call it `http`, which is an alias)
2. **Write the url only, never credentials** — the server reads `agx_config.json` itself
3. **Keep serverName unchanged** — only then do the platform-generated prefixes (`mcp__<server>__*`, `<server>__*`) stay stable
4. A 405 from `GET` is normal

### 5.2 OpenClaw

`~/.openclaw/openclaw.json`:

```json
{
  "mcp": {
    "servers": {
      "agentgeex": { "transport": "streamable-http", "url": "http://127.0.0.1:31890/agentgeex/mcp" },
      "mysql-srv": { "transport": "streamable-http", "url": "http://127.0.0.1:31890/mysql/mcp" },
      "redis-srv": { "transport": "streamable-http", "url": "http://127.0.0.1:31890/redis/mcp" }
    }
  }
}
```

After editing, run `openclaw mcp reload`. To verify: `openclaw mcp probe`.

### 5.3 Claude Code

```bash
claude mcp add -s user --transport http agentgeex  http://127.0.0.1:31890/agentgeex/mcp
claude mcp add -s user --transport http mysql-srv http://127.0.0.1:31890/mysql/mcp
claude mcp add -s user --transport http redis-srv http://127.0.0.1:31890/redis/mcp
```

**Do not hand-edit `~/.claude.json`.** That file also stores `numStartups` / `machineID` / `projects` / `tipsHistory` and the whole rest of the historical state; hand-editing or a full re-serialisation risks destroying history. Use the CLI and let it preserve the structure.

`{"type":"http"}` and `{"type":"streamable-http"}` are equivalent (the latter is an alias). **A url with no type is treated as a configuration error and skipped.**

### 5.4 Codex

`~/.codex/config.toml`:

```toml
[mcp_servers.agx-agx]
url = "http://127.0.0.1:31890/agentgeex/mcp"

[mcp_servers.agx-mysql]
url = "http://127.0.0.1:31890/mysql/mcp"

[mcp_servers.agx-redis]
url = "http://127.0.0.1:31890/redis/mcp"
```

HTTP entries **carry the url only, no type** (`type` is optional).
It is normal that the `codex` command is not on PATH — the binary ships inside the VS Code extension.

### 5.5 DeepSeek-Harness (DSH)

`~/.dsh/profiles/web/cordis.patch.yml`:

```yaml
- insert:
    - id: 'mcp-agentgeex'
      name: '@deepseek-ai/dsh-mcp-client'
      config:
        serverName: 'agentgeex'
        transport: 'streamable-http'
        url: 'http://127.0.0.1:31890/agentgeex/mcp'
        toolCallTimeoutMs: 300000

    - id: 'mcp-mysql-srv'
      name: '@deepseek-ai/dsh-mcp-client'
      config:
        serverName: 'mysql-srv'
        transport: 'streamable-http'
        url: 'http://127.0.0.1:31890/mysql/mcp'
        toolCallTimeoutMs: 120000

    - id: 'mcp-redis-srv'
      name: '@deepseek-ai/dsh-mcp-client'
      config:
        serverName: 'redis-srv'
        transport: 'streamable-http'
        url: 'http://127.0.0.1:31890/redis/mcp'
        toolCallTimeoutMs: 120000
```

DSH's HMR `config.root` is empty, so **configuration changes are not hot-reloaded; `dsh web` must be restarted**.

### 5.6 Custom clients

Any SDK supporting MCP streamable-http will do. Note:

- **Stateless**: no need to keep `Mcp-Session-Id` (the server never returns one)
- **You can POST `tools/list` directly** without a prior `initialize` (the standard flow is still recommended)
- If the client has a forward-compatibility probe (DSH sends `server/discover` first), the gateway may answer 400 — falling back to the standard `initialize` afterwards is normal; those 400s are startup noise

## 6. General steps for migrating from stdio to HTTP

Applies to any client that uses AgentGeeX MCP.

### 6.1 Mandatory before migrating

```bash
# 1. back up the client configuration
cp <config> <config>.bak_$(date +%Y%m%d_%H%M%S)

# 2. check the credentials: values in the client env == values in the server-side agx_config.json
#    if they differ, deleting the env vars will simply fail to connect. Compare booleans, never print plaintext.
```

### 6.2 ★ Handling the host-identity configuration conflict (a pitfall we hit)

If the client runs on **a host that already has AgentGeeX installed**, you will hit the `agx_config.json` conflict:

```
git merge → error: 您对下列文件的本地修改将被合并操作覆盖：agx_config.json
```
(The message means: "your local modifications to the following file will be overwritten by the merge".)

The reason: this file is tracked by git, yet it stores **each host's local identity** (`host_id` / `work_dir`). The upstream copy belongs to the author's machine. A plain merge would overwrite this host's identity with someone else's → the daemon identifies the wrong host.

Correct handling:

```bash
cp -a agx_config.json ~/.agx/backups/id_$(hostname)_$(date +%Y%m%d_%H%M%S).json
chmod 600 <backup>
git checkout -- agx_config.json          # temporarily accept the upstream version
git merge --ff-only origin/master
cp -a <backup> agx_config.json           # put the identity back
git update-index --skip-worktree agx_config.json   # exclude it from future merges
```

After `skip-worktree` local edits no longer trigger conflicts, but **if upstream changes the file again the merge fails** — which is the intended behaviour (it should never be unified upstream).

### 6.3 Migration order

```
1. start the gateway; the self-check of all three endpoints passes
2. change the client configuration (add only; leave other MCP entries alone)
3. verify tools/list counts = 100 / 5 / 7
4. run one real tool call (recommended: agx_get_global_config or check_services)
5. confirm the old stdio child processes are gone (ps should show only the gateway)
6. restart the client (only the client; the gateway does not need it)
```

### 6.4 Rollback

```bash
# OpenClaw
cp ~/.openclaw/openclaw.json.bak_<ts> ~/.openclaw/openclaw.json && openclaw mcp reload

# Claude Code
claude mcp remove -s user agentgeex && claude mcp remove -s user mysql-srv && claude mcp remove -s user redis-srv

# Codex
cp ~/.codex/config.toml.bak_<ts> ~/.codex/config.toml
```

## 7. Operational discipline

### 7.1 ★ Two kinds of change, two kinds of action (the easiest one to get wrong)

| What changed | Must do | Forbidden |
|---|---|---|
| **Service code** (`agx_mcp/*.py`) | restart the MCP service (`pm2 restart` / `systemctl restart`) | —— |
| **Connection configuration** (client URL / transport) | client `mcp reload` or client restart | —— |
| Any case | —— | **restarting openclaw-gateway** (it interrupts every conversation in flight) |

`openclaw mcp reload` means "drop the cached MCP runtime, use the new configuration from the next turn". It **does not need, and should not involve, restarting the gateway process**.

### 7.2 Verifying hot code updates

The gateway supports updating service code without restarting clients:

```
1. edit agx_mcp/*.py
2. pm2 restart agx-mcp-gateway        # restart the gateway only
3. the client's next tool call runs the new code automatically (stateless, no long connection)
```

The `service_build` fingerprint (e.g. `MCP-BUILD-20261104-0746-T1`) tells you which copy of the code is loaded.

### 7.3 Security boundary

- The gateway **binds `127.0.0.1` only** and has no authentication. If cross-machine use is ever needed, **authentication must come first**; do not simply change `--host` to `0.0.0.0`
- Credentials exist only in the server-side `agx_config.json`. No database/Redis password should appear in any client configuration — an independent security benefit of this design over stdio
- Passwords never go on the command line (they would show up in `ps` and in the logs)

## 9. Known limitations

### 9.1 The context cost of tool definitions (not caused by this design, but amplified by it)

**100 tool definitions ≈ 40.4k tokens / session** (Claude Code measured 63,036 in the first turn's input).

This is a **fixed per-session cost**, independent of the transport. It existed in the stdio era too, just unnoticed. Once unified, all platforms share the same toolset and the cost becomes conspicuous.

Possible mitigations (none implemented): tool grouping, on-demand loading, mounting by project scope. Lowering Claude Code's scope from `user` to `project` (`.mcp.json`) avoids tools unrelated to that project, but saves nothing for a session that is working on AgentGeeX itself.

### 9.2 The merge introduces new failure coupling

The three services share one process and one thread pool. Raising the thread ceiling from 40 to 120 helps, but **in extreme cases they still affect each other**: one service being CPU-bound or leaking threads drags down the other two.

What you get in return is resource savings. If one service's stability requirement outweighs the sharing benefit, use `--mount` to mount only some services, or start a second gateway instance on another port.

### 9.3 Stateless mode does not support server push

There is currently no MCP notification/subscription usage. If server-initiated messages are needed later, the gateway must return to a stateful mode (`stateless_http=False`), which brings back session-management costs.

## 10. Troubleshooting

| Symptom | Diagnosis |
|---|---|
| `GET /xxx/mcp` → 405 | **normal**, stateless mode does not stream |
| root path `/mcp` → 404 or `Session terminated` | **normal**, the services are mounted on sub-paths |
| 3 × 400 in the startup log | **normal**, the client's forward-compatibility probe (`server/discover`) is rejected and falls back |
| client cannot connect | `curl` the three endpoints first; then check the `transport` spelling; then check the url is not missing `/mcp` |
| tool count is 0 | check whether `transport` is missing (some platforms skip a server that has a url but no type) |
| tool names changed | that means `mount(prefix=)` was used instead of a path Mount — roll back immediately |
| one service slow, the other two slow too | the thread-pool ceiling is exhausted; check that `total_tokens` is 120 |
| `mcp.sh start` refused (exit code 1) | PM2 is supervising it; run `pm2 delete` first |

### Pitfall list (all of these actually happened)

1. **`$VAR` immediately followed by a CJK/full-width character must be written `${VAR}`** — bash swallows the first byte of the multi-byte sequence into the variable name and reports `pids\xef\xbc: unbound variable`. `mcp.sh` hit this 4 times. Scan for it:
   ```bash
   perl -ne 'while (/\$([A-Za-z_][A-Za-z0-9_]*)([^\x00-\x7F])/g){print "行 $.\n"}' mcp.sh
   ```

2. **`pm2 jlist` cannot be parsed with grep** — `grep -o '"name":"X"[^}]*}'` truncates at the first `}`, while `status` lives later inside `pm2_env` → online is misread as stopped → start is not refused → **once actually fought for the port**. Parse it with python.

3. **`pkill -f "<target string>"` over ssh kills the bash that carries the command** — the remote `bash -lc` command line itself contains that string. The symptom is "it stopped after two lines; the target really was killed, but all subsequent commands were lost". Workaround: the `[a]gx_mcp` regex trick, or `pgrep` for the pid first and then `kill` by pid.

4. **Matching port numbers at both ends in `lsof` ≠ the same connection** — ephemeral-port reuse fabricates false pairs (one side already closed, the port reused by another process, the snapshot glues the two sides together). To identify a client you need three pieces of evidence: **a configuration reference + the `ESTABLISHED` count + the per-process `lsof -p PID -iTCP`**.

5. **Under a Chinese locale, `ps -o lstart=` parsing fails silently** — the output is `三 11/ 4 08:04:29 2026`, which `strptime("%a %b ...")` cannot parse → a silent fallback to the pid file's mtime. What makes it dangerous is the **reverse misjudgement**: old code plus a newer pid-file timestamp is judged "already the latest code" → nobody restarts. Workaround: `LC_ALL=C`, and never let a pid found by port fall back to the pid-file timestamp.

6. **`setsid_exec(){...} &` adds an extra bash subshell layer** — `$!` is the subshell's pid, not the real process, so the pidfile is wrong and the subshell lingers. Use the inline form `python3 -c "$SETSID_SNIPPET" ... &` (`execvp` replaces in place, pid unchanged).

## Appendix C: The design judgement in one sentence

> **Service layer: one set per machine (its own daemon + gateway + MCP gateway). Data layer: one centralised source (a single MySQL + Redis).**
>
> The former ensures a machine in trouble does not drag others down; the latter ensures the whole system has exactly one source of truth. The two are not in conflict — they are two faces of the same design.
