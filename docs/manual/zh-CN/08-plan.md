# 第 8 章 计划（Plan）

计划把多个执行按依赖关系编排起来，由看门狗推进。本章说明三种拓扑、计划的三个动作、激活方式、收口通知，以及层级计划。

---

## 8.1 计划的作用

一件事超过三五个步骤、步骤之间有依赖、需要跑很久时，逐条派发难以管理。计划把这些步骤定义成一个整体，由系统按依赖关系依次放行。

| 作用 | 说明 |
|---|---|
| 依赖管理 | 前置完成才放行后置 |
| 并行 | 无依赖的步骤同时开始 |
| 汇聚 | 多个分支全部完成后才继续 |
| 进度可见 | 每一步的状态可查 |
| 收口通知 | 全部完成后通知发起方 |

## 8.3 计划状态

| 状态 | 含义 |
|---|---|
| `draft` | 已创建未激活。看门狗不扫描此状态 |
| `activated` | 已激活，步骤按依赖放行 |
| `cancelling` | 取消中 |
| `cancelled` | 已取消 |
| `completed` | 全部步骤收口 |
| `archived` | 归档 |
| `failed` | 预留状态 |

当前库中已完成 190 个，已取消 42 个，草稿 14 个，归档 5 个。

## 8.4 三种拓扑

计划由步骤组成，步骤之间的依赖用三种方式表达。

### 8.4.1 串行链

用 `prev_task` / `next_task` 把步骤首尾相连：

```
A → B → C
```

A 完成后激活 B，B 完成后激活 C。适合有严格先后顺序的工作。

### 8.4.2 扇出并行

多个步骤之间没有依赖，同时激活：

```
    ┌→ A
起点 ┼→ B
    └→ C
```

适合互不干扰的独立工作，例如同时查询多个数据源。

### 8.4.3 扇入汇聚

多个子步骤全部完成后，才激活父步骤：

```
A ┐
B ┼→ 汇聚步骤
C ┘
```

父步骤通过 `children` 声明子步骤列表。所有子步骤成功才放行父步骤，任一失败则父步骤不激活。

`children` 与 `prev_task` 互斥：一条步骤只能用一种方式表达依赖，不能同时声明子步骤与前置步骤。

## 8.5 三个动作

计划的创建、部署、激活是三件事，分开执行：

| 动作 | 方法 | 结果 |
|---|---|---|
| 创建 | `agx_plan_create` | 写入 plan 与步骤，状态 `draft` |
| 部署 | `agx_plan_deploy` | 按步骤写入执行记录，状态仍为 `draft` |
| 激活 | `agx_activate_plan` | 步骤转为 `pending`，交给看门狗推进 |

只创建不部署，没有执行记录；只部署不激活，看门狗不扫描。三步都完成后计划才开始运行。

## 8.6 两种激活方式

| `activate_mode` | 推进方式 |
|---|---|
| `watchdog` | 看门狗扫描步骤状态，按依赖放行 |
| `chain` | 链式推进，由入口执行带动后续步骤 |

两种方式的步骤初始状态一致，区别在于记录的推进策略。当前库中 `watchdog` 206 个，`chain` 45 个。

`watchdog` 是默认选择，适用于大多数场景。

## 8.7 执行者

计划的激活与推进由专用任务 `plan_execute` 承接，在独立会话中运行。它负责：

| 职责 | 说明 |
|---|---|
| 激活 | 把步骤状态从 `draft` 推进到 `pending` |
| 接收回执 | 处理各步骤的完成通知 |
| 异常处理 | 某步骤失败时的处置 |
| 收口 | 全部完成后结案并通知 |

`plan_execute` 属于 `task_type=plan`，超时读 `plan_timeout`。计划执行时间常超过普通任务，需要时可单独调大该配置。

在普通上下文中不要直接调用 `agx_activate_plan`。激活动作应通过派发 `plan_execute` 完成，这样回执与异常有统一承接者。

## 8.8 收口与通知

全部步骤完成后，计划状态置 `completed`，并发出完成通知。

| 机制 | 说明 |
|---|---|
| 通知目标 | 激活该计划的执行所对应的发起方 |
| 去重 | `notified_at` 为空的才通知，写入后不再重复 |
| 汇聚点的收口 | 父步骤需显式把 `session_key` 指向发起方会话，否则完成通知只回到激活者 |

第三条容易遗漏：扇入汇聚的父步骤如果不指定会话，最终结论会回到激活计划的会话，而计划的发起方收不到结果。

## 8.9 层级计划

目标规模较大时，用 `parent_plan_id` 建立父子关系：父计划的每个步骤激活一个子计划。

| 规模 | 做法 |
|---|---|
| 少于 15 个步骤 | 单个计划，步骤直接编排 |
| 超过 15 个步骤或包含多个独立子管线 | 父计划 + 多个子计划，父计划的步骤指向子计划 |

父计划只负责激活子计划，不关心子计划内部的步骤。判断依据是「是否包含多个可独立交付的子目标」，不是单纯看步骤数量。

## 8.10 计划操作

| 方法 | 用途 |
|---|---|
| `agx_plan_create` | 创建计划，写入 `draft` |
| `agx_plan_deploy` | 部署计划，生成各步骤的执行记录 |
| `agx_activate_plan` | 激活计划，步骤转为待执行 |
| `agx_plan_query` | 查询计划元信息与步骤状态列表 |
| `agx_plan_list` | 列出项目下所有计划及完成情况 |
| `agx_plan_cancel` | 取消计划，未开始的步骤置为 `cancelled` |

`agx_plan_cancel` 只影响 `pending` 状态的步骤，正在运行的步骤会继续执行到结束。

计划相关的派发参数：

| 参数 | 说明 |
|---|---|
| `plan_id` | 把执行关联到某个计划 |
| `prev_task` / `next_task` | 声明串行依赖 |
| `needs_confirm` | 该步骤执行成功后停在 `awaiting_confirm` 等人放行 |

## 8.11 不适用的情况

- **三个步骤以内、顺序固定**：直接逐条派发。增加一层编排就多一层失败面，出问题时排查成本更高。
- **每一步都需要人临时决定**：使用 `needs_confirm`，或由人直接执行。把决策点编排进流程不会消除决策。
- **少于 15 个步骤却使用层级计划**：父子计划只适用于包含多个独立子目标的情况，小规模使用会增加查看与排错成本。
- **在同一会话中同时执行多个计划生成任务**：每个计划应派生独立会话，混在同一会话会互相干扰。
- **在普通上下文中直接调用 `agx_activate_plan`**：异常与回执无人承接，应通过 `plan_execute` 完成。
- **创建计划后以为已在运行**：`draft` 状态不被扫描，必须部署并激活。
